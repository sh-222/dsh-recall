## [English version](./README.md)

Плагин возврата контекста для **DeepSeek Harness** (`dsh`). Крупный результат инструмента держит в
диалоге голову **и** хвост; середина уезжает в локальное хранилище SQLite под коротким id объекта, и
модель достаёт нужный кусок через `recall("<id>")` — или находит его, не угадывая смещения:
`recall("<id>", query: "…")`.

Полоса под композером показывает три числа, по которым видно, окупается ли обмен: сколько вынесено,
сколько токенов не попало в контекст и как часто модель действительно возвращалась за подробностями.

## Зачем

Измерено на 8 504 результатах инструментов из реальных сессий:

| факт | значение |
|---|---|
| результаты больше 6 КБ | 4.6% результатов |
| …и их доля во всех символах результатов | 40.7% |
| …которые больше никогда не открывают | 76% |

То есть дорогая часть сессии — это несколько гигантских результатов, которые никто не перечитывает.
Их вынос убирает токены, которые иначе **переотправлялись бы на каждом следующем шаге**: экономия
составляет `removed_tokens × remaining_steps × cache_price`, а не просто `removed_tokens`.

Потолок, честно: результаты инструментов — это примерно 46% контекста, поэтому вынос *всех* всё
равно ограничен примерно 18% контекста. На маршруте, где чтение кеша стоит почти как входной токен,
это реальные 20–25% длинной сессии; на first-party маршруте с дешёвым кешем — единицы процентов, и
там рычаг — свежий ввод и число шагов.

## Возможности

- **Голова и хвост, а не только голова** — хвост — это место, где инструменты держат свои подсказки
  для повторного чтения и итоги. Срез только по голове их выбрасывает, поэтому штатное
  spill-уведомление (`Full formatted result stored at: …`) сохраняется целиком, вместе со скобкой.
- **Гейт по бюджету** — есть режим, в котором вынос происходит только пока поверхность реально
  превышает бюджет токенов (`budgetTokens`): ничего не сокращается ради экономии, которая не нужна.
- **Replay-safe замена** — та же пара, что у штатного pruner: событие `compaction/prune`, которое
  оценивает и цитирует затенённый узел, затем `tool/result` с `surfaceOp: {op:'replace'}`.
  Durable-лог хранит оригинал, поэтому возобновлённая сессия воспроизводится один в один.
- **Структурная идемпотентность** — база помнит, какие пары `(session, seq)` уже вынесены, поэтому
  инструмент, который просто *напечатал* маркер `[recall]`, не заставит сборщик пропустить
  настоящий результат.
- **Нетекстовые блоки выживают** — картинки в результате переезжают без потерь; сокращается только
  текст.
- **Безопасно для code points** — срезы и подсчёт идут по code points Unicode, поэтому суррогатная
  пара никогда не разрезается пополам.
- **Поиск в recall** — `recall(id, query: "…")` возвращает совпавшие строки с настоящими смещениями,
  так что модель прыгает сразу в нужное место, а не делит пополам 200-килобайтный лог.
- **Хранилище с дедупликацией и сжатием** — один файл SQLite, нагрузки сжаты deflate и адресуются по
  SHA-256 исходного текста: один и тот же вывод, прочитанный дважды, хранится один раз.
- **Ретенция, которая есть** — `maxAgeDays` и `maxBytes` вытесняют сначала самые старые и подчищают
  блобы, на которые больше никто не ссылается.
- **Точный учёт токенов** — экономия считается токен-метром харнесса, а не `chars / 4`.
- **Полоса** — компактная пилюля в `shell.overlay`: выносы, токены, не попавшие в контекст,
  обращения к recall и занятое место на диске.
- **Деградирует, а не ломается** — недоступное или неподдерживаемое хранилище пишет одну строку в
  лог, профиль грузится, а `recall` сообщает, что хранилище недоступно.

## Требования

| | |
|---|---|
| `dsh` | `>= 0.2.0-0` (объявлено в `package.json`) |
| Node | `>= 22.5` для хранилища (`node:sqlite` — модуль стандартной библиотеки) |
| Профиль | любой для host-половины; **web** для полосы (`dsh.client.platform: web`) |

На более старом Node плагин всё равно загружается, и инструмент `recall` отвечает — просто сообщает,
что хранилище недоступно, потому что класть его некуда.

## Установка

Профиль web / TUI:

```sh
dsh plugin --profile web add github:sh-222/dsh-recall
```

Профилем Electron **desktop** нельзя управлять из CLI by design. Добавь зависимость и строку бандла
в `~/.dsh/profiles/desktop/package.json`, затем установи:

```json
{
  "dependencies": { "dsh-recall": "github:sh-222/dsh-recall" },
  "dsh": { "profile": { "bundles": ["…", "dsh-recall"] } }
}
```

```sh
cd ~/.dsh/profiles/desktop && pnpm install --ignore-scripts
```

Перезапусти харнесс. Плагин загружается только при старте.

### Обновление и удаление

```sh
dsh plugin --profile web remove dsh-recall   # либо правь строку бандла и pnpm install
```

Хранилище в `~/.local/share/dsh-recall/` — твоё, и удаление плагина его не трогает; удали, когда
объекты больше не нужны.

История релизов — в [CHANGELOG.md](CHANGELOG.md).

### Установка из локального чекаута

`dsh plugin --profile <p> add ~/Projects/dsh-recall` пишет зависимость `link:`, а **node резолвит
`@deepseek-ai/*` от реального пути**, а не через профиль — поэтому `link:`-чекаут падает с
`ERR_MODULE_NOT_FOUND`, пока не сделаешь симлинки один раз:

```sh
cd ~/Projects/dsh-recall && mkdir -p node_modules/@deepseek-ai
DSH="$(dirname "$(dirname "$(readlink -f "$(command -v dsh)")")")/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai"
for pkg in dsh-llm dsh-tools schemastery; do ln -sfn "$DSH/$pkg" node_modules/@deepseek-ai/; done
```

## Использование

### Что происходит с крупным результатом

1. Результат инструмента попадает на поверхность.
2. На следующем вызове инструмента каждый результат **старше новейших `keep`** и **длиннее
   `thresholdChars`** переписывается в `голова + заметка [recall] + хвост`.
3. Середина пишется в хранилище под `md5(session:seq:chars)[:8]`, например `#4d3661d2`.

Модель видит это вместо 4 000 символов вывода:

```
XXXX… (600 символов головы) …

[recall] read call_A — 4000 chars total. The head and tail are above and below; the middle 3160
chars are stored as object #4d3661d2. Fetch any part with recall("4d3661d2") (optionally
recall("4d3661d2", start, count)), or search it with recall("4d3661d2", query).

XXXX… (240 символов хвоста, либо целое spill-уведомление, если оно было)
```

Ничего не удаляется: полный текст остаётся и в логе сессии, и в хранилище.

### Инструмент `recall`

| вызов | результат |
|---|---|
| `recall("4d3661d2")` | первые 8 000 символов |
| `recall("4d3661d2", start, count)` | диапазон символов (жёсткий предел 24 000 за вызов) |
| `recall("4d3661d2", query: "FATAL")` | до 20 совпавших строк с их смещениями |

Смещения — в code points, в тех же единицах, что и в заметке, поэтому число из результата поиска
можно сразу подставить в вызов с диапазоном.

### Полоса

Компактная пилюля в `shell.overlay`. Пристёгивается прямо над бейджем **dsh-tidewatch**, если тот
установлен: она читает элемент `[data-dsh-tide-anchor]`, который tidewatch экспортирует (а на старых
установках — `.tw-chip`), и две пилюли читаются как одна карточка; без tidewatch — угол внизу справа.
Больше с tidewatch ничего не связано: плагины остаются независимыми пакетами со своими релизами.

По клику раскрываются последние 12 выносов с именем инструмента, размером и возрастом, плюс занятое
место на диске. Данные берутся из `GET /recall/api/stats` на loopback-порту хоста, опрос раз в 12 с:

```json
{
  "offloaded": 196,
  "charsSaved": 1207034,
  "tokensSaved": 301759,
  "recalls": 12,
  "bytes": 1834211,
  "rawBytes": 4021337,
  "threshold": 2500,
  "head": 600,
  "tail": 240,
  "keep": 2,
  "budgetTokens": 0,
  "maxBytes": 0,
  "recent": [{ "session": "…", "seq": 82, "tool": "read", "id": "4d3661d2", "chars": 4000, "ts": 1793906054462 }]
}
```

Все числа, кроме `recalls`, — агрегат по хранилищу, поэтому рестарты и второй процесс харнесса не
могут их развести.

## Настройка

Все ручки — это конфиг плагина, проверяемый при загрузке (неизвестный ключ — ошибка, а не тихий
no-op):

```yaml
- id: dsh-recall
  name: dsh-recall
  config:
    thresholdChars: 2500   # выносим только то, что длиннее
    headChars: 600         # остаётся в контексте в начале
    tailChars: 240         # остаётся в конце (там инструменты держат подсказки)
    keep: 2                # последние результаты не трогаем
    budgetTokens: 0        # 0 = вынос по порогу; >0 = только пока превышен бюджет
    spillNoticeChars: 600  # запас хвоста на целое spill-уведомление (0 отключает)
    maxAgeDays: 0          # 0 = хранить вечно
    maxBytes: 0            # 0 = без потолка; >0 вытесняет сначала старые
    enabled: true          # выключить сборщик, оставив recall(id)
    stateDir: ~/.local/share/dsh-recall
```

`thresholdChars: 2500 / headChars: 600` выбраны по распределению размеров из 12 реальных сессий
(1 150 результатов, 487 тыс. токенов), а не на глаз:

| порог | голова | результатов задето | сэкономлено | доля объёма | объектов на recall |
|---|---|---|---|---|---|
| 6 000 | 1 200 | 40 | 114 тыс. ток | 23.5% | 40 |
| 4 000 | 600 | 103 | 186 тыс. ток | 38.1% | 103 |
| **2 500** | **600** | 218 | 258 тыс. ток | **53.0%** | 218 |
| 1 500 | 600 | 368 | 308 тыс. ток | 63.3% | 368 |

2 500 / 600 — это колено: покрытие удваивается по сравнению с 6 000, а число объектов остаётся около
18 на сессию. Переход на 1 500 даёт десять пунктов объёма за тройное число объектов — больше шансов,
что модель погонится за указателем там, где перечитать было бы дешевле. Голову ниже нескольких сотен
символов не опускать: модель должна видеть форму результата.

**Читай отношение `recalls / offloaded` как результат эксперимента.** Около нуля — содержимое не
понадобилось. Близко к единице — голова мала, поднимай `headChars` примерно до 2 000, прежде чем
трогать остальное. Между ними — инструмент окупается.

## Хранение

```
~/.local/share/dsh-recall/store.db    одна база SQLite (WAL)
```

Три таблицы:

| таблица | что держит |
|---|---|
| `objects` | id, session, seq, tool, учёт символов и токенов, время |
| `blobs` | нагрузка, сжатая deflate, ключ — SHA-256 исходного текста |
| `counters` | только `recalls`; всё остальное — агрегат |

База вместо каталога файлов даёт четыре вещи: одинаковый вывод хранится один раз, нагрузка сжимается
— насколько, зависит от текста: повторяющийся вывод инструментов уменьшается на порядок, смешанный
текст с кодом примерно в 2–4 раза — цифры полосы это один запрос вместо полного разбора индекса, и
два процесса могут писать параллельно без «побеждает последний».

Один плоский пул на `$HOME`, общий для всех проектов. Id = `md5(session:seq:chars)`. Смотреть можно
любым SQLite-клиентом:

```sh
sqlite3 ~/.local/share/dsh-recall/store.db \
  'select tool, chars, datetime(ts/1000,"unixepoch") from objects order by ts desc limit 5'
```

Апгрейд с раскладки 0.3 (`objects/*.txt` + `index.jsonl`) импортируется при первом запуске, а JSONL
переименовывается в `index.jsonl.migrated`; старые id продолжают открываться и сохраняют исходные
метки времени.

**Ретенция.** Если заданы `maxAgeDays` / `maxBytes`, хранилище вытесняет при открытии и после каждого
64-го выноса, сначала самые старые, затем удаляет блобы без ссылок и возвращает страницы файловой
системе (`auto_vacuum = INCREMENTAL`). Удаление объекта ломает указатели на него — это неизбежное
свойство любого потолка, поэтому по умолчанию не удаляется ничего.

## Как это работает

Сборщик — это слушатель waterfall-хука `tools/post-execute`, того же, что использует штатная
spill-политика:

1. снять снимок поверхности и найти узлы `tool/result`;
2. отбросить новейшие `keep` и всё, что не длиннее `thresholdChars`;
3. для каждого кандидата получить сообщение, срезать голову и хвост и пропустить замену, если
   указатель не короче оригинала;
4. добавить `compaction/prune` (оценивает и цитирует затенённый узел), затем `tool/result` с
   `surfaceOp: {op:'replace', startSeq, endSeq}` и `sourceEventSeqs: [seq]`;
5. записать объект в хранилище и остановиться, когда бюджет токенов удовлетворён.

Две детали держат горячий путь дешёвым: множество уже рассмотренных seq на сессию (результат
обрабатывается один раз, а не на каждом вызове инструмента) и подготовленные выражения в хранилище
(проверка кандидата — это индексный поиск, а не разбор).

## Чего плагин не делает: сжатие на 15%

`dsh-recall` никогда не решает, *когда* сжимать контекст, и не трогает окно контекста. Процентное
сжатие — это штатный плагин `@deepseek-ai/dsh-compaction-basic`, настроенный в собственном слое
патча профиля (`~/.dsh/profiles/<profile>/cordis.patch.yml`):

```yaml
- id: compaction-basic
  name: "@deepseek-ai/dsh-compaction-basic"
  config:
    thresholdRatio: 0.15
    retainRatio: 0.05
```

`thresholdRatio` — доля окна модели, при которой начинается проход сжатия; `retainRatio` — доля,
остающаяся после него. Штатные значения — `0.8` / `0.16`. На этой машине профиль desktop работает с
`0.15 / 0.05`, то есть окно 256k сжимается на ~38k токенов и оставляет ~13k — заметно меньше, чем
позволяет модель. Это и есть ручка, которую стоит поднять, если нужно больше места:

```yaml
thresholdRatio: 0.6   # сжимать на 60% окна вместо 15%
retainRatio: 0.15
```

Механизмы независимы и дополняют друг друга: сжатие переписывает *всю* историю в саммари, когда окно
заполняется, а `dsh-recall` оставляет историю целой и только укорачивает отдельные крупные
результаты — именно это отодвигает момент, когда сжатие вынуждено запуститься. Выключение recall не
меняет 15%, а подъём 15% не меняет то, что делает recall.

Ещё два штатных плагина полезно знать, потому что они перекрываются by design:

| плагин | что делает | чем recall отличается |
|---|---|---|
| `dsh-spill-policy` (`maxInlineTokens: 12500`) | выносит слишком крупный *входящий* результат в файл и оставляет уведомление с локатором | recall работает **ретроактивно** по результатам, уже лежащим на поверхности, и при гораздо более низком пороге — и сохраняет spill-уведомление целым, когда срабатывают оба |
| `dsh-compaction-tool-result-pruner` (`8192 / 4096 / 1024`) | подрезает старые результаты **во время** прохода сжатия | recall действует на каждом вызове инструмента, поэтому давление, которое запускает сжатие, наступает позже |

## Язык интерфейса

Полоса следует языку интерфейса: копия на английском и русском, числа и длительности форматируются
через `Intl` для активной локали (`ru-RU` или `en-US`). Всё остальное откатывается на английский.

| `test/client-harness.mjs` | клиентская половина монтируется, регистрирует запись в `shell.overlay` и позиционируется от якоря |

`npm test` работает в двух окружениях. В чистом чекауте — свежий клон, раннер CI — три пробы, которые
импортируют host-половину (`reaper`, `realsession`, `http-harness`), печатают `skip — …` и выходят с
кодом 0, а `store` и `client-harness` выполняются; именно на это опирается релизный workflow, потому что
ставить туда весь харнесс — это ~80 с на каждый релиз и всё равно другая версия харнесса, чем у вас.
Внутри профиля dsh или после `npm install --no-save @deepseek-ai/dsh` прогоняются все пять.
Терпится только отсутствие `@deepseek-ai/*`: любой другой отсутствующий модуль валит пробу.

Проба клиента появилась из-за реальной регрессии: `slots.register()` возвращает disposer, а не
промис, поэтому `.catch()` на нём бросал `TypeError: slots.register(...).catch is not a function`, и
пилюля не монтировалась. Харнесс воспроизводит настоящий фасад (thenable-функция без `.catch`) и
рендерит компонент один раз, refs до эффектов, как это делает React.

## Честные ограничения

- **Указатель полезен, пока голова объясняет, что это был за результат.** Поэтому в заметке есть имя
  инструмента и полный размер.
- **Последний крупный результат сессии не выносится никогда.** Хук срабатывает до того, как текущий
  результат попадёт на поверхность, поэтому сборщик видит только более ранние; должно прийти что-то
  новее.
- **Текстовые блоки схлопываются в один.** Результат из нескольких текстовых блоков сохраняет порядок
  текста и картинки, но картинка, стоявшая *между* двумя блоками, переезжает после них.
- **Маркер `[recall]` — консервативный предфильтр.** Настоящий результат, в котором случайно есть
  литерал `[recall]`, не трогается.
- **Возобновлённые сессии стартуют с пустой картой `callId → имя`**, поэтому результат, вынесенный
  сразу после рестарта, может быть подписан `tool` вместо `read`. Косметика.
- **Ретенция ломает старые указатели by construction.** При заданных `maxBytes`/`maxAgeDays`
  удалённый объект отвечает `not found`.
- **Два экземпляра харнесса делят один пул.** SQLite сериализует их записи (`busy_timeout`); все
  числа полосы, кроме `recalls`, вычисляются из таблиц, поэтому разойтись не могут.
